# Results manifest

Where every published number comes from. Nothing in `results/` or `data/` is edited after it is written: episode files are append-only records from the runner, summaries and charts are regenerated from them byte for byte, and archived development stages are unchanged snapshots.

**One command checks every headline number:** `python3 src/headline_results.py` recomputes each claim in the README from the committed files and compares it with the published value (exit status 1 on any mismatch; CI runs it). The claim keys below are the keys in that script.

## Validity and exclusion rules (as frozen)

- A call with any control violation makes its episode `invalid_run`. The episode is not graded, stays in the denominator, and stops the batch. V1's checks cover the init metadata, native tool use, MCP servers, overage, the assistant model ID and any stderr output. V2 adds checks for the CLI version, any server-side tool, any model other than `claude-opus-5` in the usage report, and any non-message usage iteration. **Scored runs: 0 invalid in V1 and 0 in V2.**
- Timeouts, malformed output, refusals and wrong units are outcomes. They are graded incorrect, not deleted. Scored runs had 0 timeouts and 0 malformed final answers.
- No scored episode was excluded, repeated or added. The scored plans ran once, and resume never repeats an attempted episode (`duplicates 0; unplanned 0` in `summary_scored.md`).
- V2 development stages 1–2 are **void**: a second model ran inside most of their calls. They are archived, not deleted, and appear in no reported rate except the contamination count.
- V2 development stage 3's no-tool records were superseded by stage 4 after Leo's wording decision V2-4b. They are kept as a finding. The grader, tolerance and tasks were not changed on any development outcome.

## Reproduce (no model calls, Python 3.11 standard library)

```bash
python3 -m unittest discover -s tests          # offline test suite
python3 src/headline_results.py                # every headline number vs its published value
python3 src/analyze.py && python3 src/chart.py
python3 src/analyze_v2.py scored && python3 src/chart_v2.py scored
python3 src/analyze_v2.py dev && python3 src/chart_v2.py dev
git status --short results/                    # prints nothing: regenerated files are byte-identical
```

## What the public repository cannot regenerate

- **The raw-trace basis of the 31/48 audit.** The public evidence is the two committed audit files, one entry per call. `src/headline_results.py` checks that they cover exactly the calls in the archived stage records and that their totals are internally consistent. The stage 1–2 episode records predate the per-call `models_used` field (schema v2.1), so the records alone cannot recount the second model. On the author's machine, with `results/raw/` present, the same script re-derives every call from its raw trace using the V2 runner's own control logic. On 2026-09-27 it gave: 31/48 calls with a second model (agreeing with the audit files call by call, 48/48); 48/48 clean development calls in stages 3–4; 324/324 scored V2 calls and 24/24 scored V1 calls with `claude-opus-5` only and no server-side tool.
- **The two development calls outside the repository** (a smoke check and the advisor probe). They are recorded in the protocol and the log; their traces are not in `results/raw/`.
- **The model calls themselves.** A rerun needs the frozen CLI version and a Claude subscription. Outputs are sampled, and the serving stack behind a model ID can change unobservably. No reported number depends on a rerun. The runners refuse to start unless every frozen file matches its manifest. The frozen modules' docstrings were edited after release, so a rerun would have to start from the release tag (CI checks that the frozen code is unchanged apart from docstrings).
